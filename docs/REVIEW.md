# REVIEW · 协作流程与验收标准

> ⚠️ **协作模式已变更**（2026-10-09）：由「你写代码，我评审」改为
> **「我写代码 + 逐步教学，你验收与提问」**。
> 原因：代码量已经超出你独立完成的速度，写不出来的部分硬写只会拖慢进度。
> 详见本文档 **第 10 节**。

[1] 我出任务卡 ──▶ [2] 我写代码 ──▶ [3] 我自检 ──▶ [4] 我讲解 ──┘
   (验收标准)      (含测试)        (跑通+测试)    (设计决策/坑/面试预演)

**我的每次交付固定六项**（第 10.4 节）：实现了什么 / 关键设计决策 /
踩的坑 / 验证输出 / 面试追问预演 / 你的行动项。
漏了任何一项，你直接指出来。

### 具体怎么提交给我评审

> ⚠️ **以下为旧模式（你写代码 → 我评审）的流程，现保留作为参考。**
> 当前模式下代码由我写，本节暂不适用；但"卡住时怎么描述问题"的模板
> 在你向我提问时仍然有效（见第 7 节）。

在会话里告诉我，并附上信息：

```
阶段: S1-W3
任务: 训练循环工程化
改动: recagent/train/loop.py (新增), tests/test_loop.py (新增)
自检: pytest 全绿；MLP 梯度对齐误差 3.2e-7
卡点: DataLoader 的 num_workers>0 在 Windows 下报错，已用 0 绕过
问题: loop.py 里 early stop 逻辑放在类里还是回调里更合适？
```

**我会给你**：

1. **正确性检查** —— 公式、维度、边界、数据泄漏
2. **设计评审** —— 接口是否合理、职责是否清晰、抽象是否过度
3. **面试视角** —— 这段代码如果被面试官追问，会问什么、你能答上吗
4. **改进清单** —— 分「必须改」「建议改」「可以不管」三档

## 2. Definition of Done（每个任务完成的定义）

一个任务算完成，必须**同时**满足：

- [ ] **功能**：实现符合 `docs/ARCHITECTURE.md` 的接口契约
- [ ] **测试**：核心逻辑有单元测试；边界条件有覆盖；`pytest` 全绿
- [ ] **类型**：有类型注解；`ruff` 和 `mypy` 无报错
- [ ] **可复现**：随机种子固定；配置走 yaml；有运行命令记录
- [ ] **可观测**：关键步骤有日志；训练有 loss 曲线（存到 `reports/`）
- [ ] **文档**：模块有 docstring 说明**为什么**这么做；复杂逻辑有注释
- [ ] **评审**：已通过我的评审，必须改项已处理
- [ ] **提交**：commit message 规范（见下）

> 注意：**"跑通了"不等于"做完了"**。跑通只是起点。
> 一个没有测试、没有复现记录的训练脚本，两周后你自己都不敢重跑。

## 3. 各阶段专属验收重点

| 阶段 | 我会重点查什么 | 常见翻车点 |
| --- | --- | --- |
| S0 | 环境可复现性、CI 是否真跑 | 依赖没锁版本，换机器就崩 |
| S1 | 反向传播推导、梯度数值对齐 | 手写版本和 PyTorch 对不上却"看着差不多" |
| S2 | 张量维度推导、attention 实现 | reshape/transpose 搞混，多头实际退化成单头 |
| S3 | **数据泄漏**、负采样、指标实现 | 时间切分边界处理错，测试集信息漏进训练 |
| S4 | 指令数据构造、评测公平性 | 数据泄漏；用 prompt 效果冒充微调效果 |
| S5 | 压测方法、量化评估 | 只测单请求延迟；量化只看均值精度 |
| S6 | ReAct 终止条件、评测方案 | 死循环；评测全靠"我看着还行" |
| S7 | 消融公平性、表述严谨 | 数字对不上；结论超出实验支撑范围 |

### S3 数据泄漏专项（我会逐条查）

这是推荐系统最容易出错、也最容易被面试官抓到的地方：

1. 时间切分的分界点是否严格按时间戳，有无同一时间戳跨越切分
2. 特征里有没有用到未来信息（如用全量数据算的物品统计量）
3. 负采样是否只从用户未交互且**在切分点之前已存在**的物品中采
4. embedding 的初始化/预训练是否用过测试集
5. 早停是否用了测试集（必须用验证集）

## 4. 代码规范

### 命名

- 类 `PascalCase`，函数/变量 `snake_case`，常量 `UPPER_SNAKE`
- 私有方法前缀 `_`
- **不用拼音**，不用 `data1` `tmp` `aaa`

### 函数

- 单个函数 ≤ 50 行，超过就拆
- 参数超过 4 个就用 dataclass 封装配置
- 禁止裸 `except:`，必须捕获具体异常
- 禁止用 `print` 调试后留在提交里（用 `logging`）

### 提交信息

```
<type>(<scope>): <subject>

feat(s1): 实现两层 MLP 反向传播与数值对齐测试
fix(s3): 修正时间切分边界，避免同一时间戳跨界
docs(s2): 补充 MHA 张量维度推导笔记
refactor(engine): 抽取召回通道为 Protocol
test(s1): 增加梯度对齐边界用例
```

type: `feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`

**禁止**：`update`、`fix bug`、`修改`、一次提交改 20 个不相关文件。

### 禁止事项

- ❌ 提交数据集和模型权重（用 `.gitignore` + 下载脚本）
- ❌ 提交 `.ipynb` 的输出（用 `nbstripout`）
- ❌ 硬编码路径（`C:\Users\...`），一律走配置
- ❌ 硬编码超参，一律走 yaml
- ❌ `from x import *`

## 5. 实验记录规范

每个实验必须在 `reports/` 留下记录，包含：

```markdown
# 实验: SASRec 在 ML-1M 上的基线

## 配置
- config: configs/model/sasrec_ml1m.yaml
- git commit: a1b2c3d
- seed: 42, 43, 44（跑 3 次取均值±标准差）

## 环境
- GPU: RTX 3060 Laptop 6GB
- torch: 2.x.x, cuda: 12.6

## 结果
| 指标 | seed42 | seed43 | seed44 | 均值±std |
| --- | --- | --- | --- | --- |
| NDCG@10 | | | | |

## 观察
- 什么现象？和预期一致吗？

## 结论
- 下一步做什么？
```

**三条硬规矩**：

1. 所有实验跑 **≥3 个随机种子**，报告均值±标准差。单次结果不算数。
2. 报告必须带 **git commit hash**，否则无法复现。
3. 结论**不许超过数据支撑范围**。"效果更好"要带数字，"更好是因为 X"要有消融证据。

## 9. 对 AI 产出的检查清单

> 这一节来自一次真实的复盘：S0–S1 期间 AI 交了十几次错，
> 逐个归因后发现错误集中在 5 类，且**多数与上下文长短无关**，而是方法问题。
>
> 这份清单有两个用途：
> 1. **你用来审查我的产出**（最重要）
> 2. 你自己做实验、写论文、带实习生时，同样适用

### 9.1 五条硬规则

| # | 规则 | 针对的错误类型 | 怎么落地 |
| --- | --- | --- | --- |
| 1 | **实验类工作先做「信号有效性检查」** | 设计疏漏 | 先跑 1 个配置，确认"目标现象能观察到、对比指标有区分度"，再铺开全量 |
| 2 | **修完模式类问题必须扫同类** | 治标不治本 | 在 commit message 里写明"已扫描的同类位置" |
| 3 | **外部库的边界行为先跑 3 行验证** | API 假设 | 不凭记忆写；类型接受度、默认值、版本差异都要实测 |
| 4 | **结论性输出回到原始数据核对字段** | 未验证就交付 | 报告/commit 里的每个数字，都要能指回日志来源 |
| 5 | **关键决策落文件，不依赖记忆** | 长上下文丢失 | 写进 `docs/DECISIONS.md` 或 `reports/`，而不是"记得说过" |

### 9.2 每条的由来（真实案例）

| 规则 | 触发它的具体错误 |
| --- | --- |
| 1 | 训练负样本动态采样 + 评测固定 → 指标失真，白跑 40 分钟。若先花 5 分钟检查信号，可省 35 分钟 |
| 1 | 模型容量不足 → 最优轮次恒为 0，根本观察不到过拟合，实验设计本身无效 |
| 2 | `.gitignore` 的 `data/` 忽略掉代码包，修完后**没检查** `models/`，同一个坑犯两次 |
| 3 | `logger.info("{}", x)` —— 标准 logging 只支持 `%s`；`torch.sqrt(0.0)` —— torch 2.14 拒绝 Python float 标量 |
| 4 | 报告写了"早停生效"，实际 `stopped_early=False`（轮数不够，从未触发） |
| 5 | `.gitignore` 的同一错误重复出现，因为约定没落文件 |

### 9.3 你要问我的五个问题

| 场景 | 追问 |
| --- | --- |
| 我给出结论或数字 | **"原始日志在哪？"** —— 让我指回具体输出 |
| 我修了一个模式类问题 | **"同类还有几处？"** |
| 我写实验设计 | **"怎么确认这个实验的信号可信？"** |
| 我引用某个库的行为 | **"跑一段最小代码验证给我看"** |
| 我跑出"很好的结果" | **提高警惕** —— 好得反常通常是泄漏或协议错配 |

### 9.4 一条反向经验

**"结果很好"比"结果很差"更危险。**

结果差你会去查；结果好你会直接采信。S1-W3 那次 `train_loss = 0.6931 = ln(2)`
看着像"收敛得漂亮"，实际是模型输出恒为 0 —— 如果没去核对 `ln(2)` 这个值，
整个实验结论就是错的。

**所以：任何异常"好"或"整齐"的数字，先怀疑，再采信。**

## 10. 协作模式（2026-10-09 起）

### 10.1 变更内容

| 项目 | 旧模式 | **新模式** |
| --- | --- | --- |
| 写代码 | 你写 | **我写** |
| 你的角色 | 实现 + 学习 | **验收 + 提问 + 理解** |
| 教学方式 | 我评审你的代码 | **我写完后详细讲：为什么这么设计、踩了什么坑、面试会怎么问** |
| 你仍必须做的 | —— | ① 看懂关键设计 ② 能回答面试追问 ③ 独立复跑验证命令 |

### 10.2 为什么改

写不出来的部分硬写会拖慢进度，且容易打击信心。
更重要的是：**这个项目的目标是"能讲清楚"，不是"每个字符都自己敲"**。

面试官不会问你"这行是不是你打的"，他会问：
- 你为什么这样设计？
- 遇到什么问题？怎么发现的？
- 换成别的方案会怎样？

这三类问题靠**理解**回答，不靠手速。

### 10.3 但有一条底线不能松

**"我写完了"不等于"你学会了"。**

每个阶段结束后，你必须能：
1. 用自己的话复述核心设计决策（至少 3 个）
2. 回答该阶段的面试追问（`docs/interview/` 里有题）
3. 独立跑一遍验证命令，并解释输出

**做不到第 3 条，说明这个阶段白做** —— 因为面试时你没法现场"跑一下看看"。

### 10.4 每轮交付的固定结构

我每次写完代码，会按这个结构给你讲解：

```
① 这轮实现了什么（一句话）
② 关键设计决策 N 个（每个含：为什么这么选 / 不这么选会怎样）
③ 过程中踩的坑（如果有）
④ 验证结果（原始输出，可复跑）
⑤ 面试追问预演（这段代码会被问什么）
⑥ 你的行动项（看懂什么、跑什么命令、答什么问题）
```

**如果哪一轮我漏了任何一项，你直接指出来。**
