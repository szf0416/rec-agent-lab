## ADR-001: 项目定位为「推荐系统 + LLM Agent」交叉项目

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

用户研究方向为推荐系统，已有 LightGCN / BPR / MBGCN / S-MBRec / MultiRec / RecBole 复现经验，
但缺乏大模型与 Agent 工程经验。目标岗位为 AI 算法工程师 / Agent 工程师，时间窗 11 个月（至 2026 年 8 月秋招）。

约束：
- 本地算力 RTX 3060 Laptop 6GB（空闲约 2.6GB）
- 云 GPU 预算仅几百元
- 不追求发论文，追求「能力全覆盖 + 可展示 + 可讲」

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A. 纯 Agent 项目（RAG 问答/多智能体） | 岗位面最宽 | 与推荐系统背景割裂；同质化严重，无护城河 |
| B. 纯 LLM4Rec 论文复现 | 贴近研究方向，利于科研 | 无工程与部署内容；算法工程岗说服力弱 |
| C. 推荐系统 + LLM Agent 交叉 | 两层深度；工具调用真实模型，非套壳；护城河强 | 体量大，需要 11 个月持续推进 |

### 决策

选择 **C**。以自训推荐模型作为 Agent 的"手脚"，Agent 调用真实模型而非只有 prompt。

### 后果

- **正面**：
  - 简历可讲两层：底层模型能力 + 上层 Agent 工程能力
  - 消融实验天然成立（每一层都有对照），面试素材丰富
  - 与已有推荐系统积累直接衔接，复用了 RecBole 等经验
- **负面**：
  - 工作量约为纯 Agent 项目的 2–3 倍，存在半途而废风险
  - 必须严格分阶段推进，任一阶段拖延都会挤压后期
- **重新考虑的触发条件**：
  - 若 S3 结束（约 2026 年 4 月）指标明显不达标，则砍掉 S4 的 DPO 和 S5 的剪枝，保 Agent 主线
  - 若求职方向中途变为纯 Agent 岗，可把 S6 提前

## ADR-002: 主数据集选 MovieLens-1M

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

需要一个能在 6GB 显存上完整训练、且社区基线丰富的数据集。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **MovieLens-1M** | 本地已有；100 万评分；6GB 够训；论文基线多；含用户人口统计特征（利于 LLM 生成画像） | 规模偏小，不够"大数据" |
| Amazon Reviews | 稀疏、真实、长尾明显 | 体量大，6GB 训练吃力；清洗成本高 |
| Yelp / Taobao | 工业级规模 | 太大，超出硬件能力 |

### 决策

主数据集 **MovieLens-1M**，Amazon Electronics 子集仅用于**冷启动/长尾专项实验**。

### 后果

- 正面：迭代快（一次全量训练分钟级），消融实验可以跑很多组
- 负面：面试可能被质疑"数据集太小，没处理过工业规模"
  - **应对**：在报告中明确说明是硬件约束下的选择，并给出
    "若扩展到亿级，架构上需要改什么"的分析（分片、负采样、ANN 索引选型）
- 重新考虑：若获得云 GPU 支持，追加一个 Amazon 全量实验

## ADR-003: 数据切分采用时间切分（而非随机切分）

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

推荐系统评测的切分方式直接决定指标是否可信。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 随机切分 | 实现简单；与部分论文可比 | **未来信息泄漏**，指标虚高，与线上不一致 |
| **时间切分** | 无泄漏；贴近线上；面试加分 | 实现复杂；与部分论文不可比 |
| Leave-one-out | 与主流论文（SASRec/BERT4Rec）对齐 | 仍有轻微泄漏；单样本评测方差大 |

### 决策

**时间切分为主**（80/10/10），**同时支持 leave-one-out** 用于与论文基线对齐。
两种切分都必须实现，报告中同时给出。

### 后果

- 正面：数据可信；能讲清"为什么工业界用时间切分"
- 负面：指标会比随机切分低一截，需要能在报告中解释差异来源
- 重新考虑：无。这是正确性问题，不是偏好问题。

## ADR-004: 评测指标自己实现，不用 RecBole 直接算

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

用户已有 `recbole-ml1m-amazon` 仓库的 RecBole 使用经验。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 直接用 RecBole | 快、省事、社区认可 | 面试问"NDCG 怎么算"答不上细节；无法定制指标 |
| **自己实现 + RecBole 交叉校验** | 真正理解；可定制；可讲推导 | 需要额外写测试和对照 |

### 决策

自己实现全部指标，用 RecBole 的结果做**交叉校验**并出具对照表。

### 后果

- 正面：面试高频考点（NDCG/HR/MRR 的推导与适用场景）能答透
- 负面：多花约 1 周；需要处理两套实现的细节差异（如是否去重、是否过滤已看）
- 重新考虑：无

## ADR-005: Agent 框架自研 ReAct 为主，LangGraph 作对照

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

Agent 工程师岗位既考察"会不会用框架"，也考察"懂不懂原理"。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只用 LangGraph/LangChain | 开发快，简历关键词匹配 | 容易被质疑"套壳"；细节被框架隐藏，追问即露底 |
| **自研 ReAct + LangGraph 对照** | 两头都占：理解本质 + 会用工具 | 工作量增加约 2 周 |

### 决策

S6 先用纯 Python 自研 ReAct 循环（含容错、超时、去重），再用 LangGraph 重写编排，
两个版本都保留，报告中对比优劣。

### 后果

- 正面：能回答"ReAct 循环具体怎么实现的""框架帮你做了什么"，这是区分度所在
- 负面：需要自己处理框架免费提供的东西（状态持久化、并发、重试）
- 重新考虑：若 S6 时间紧张，可只保留自研版本，把 LangGraph 降级为"读过源码"的谈资

## ADR-006: LLM 基座选 Qwen2.5 系列，微调用 QLoRA

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

6GB 显存约束下需要做 LLM 微调，且面向中文场景与中文简历。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **Qwen2.5-1.5B/7B-Instruct** | 中文强；1.5B↔7B 梯度完整可做对照；生态成熟；QLoRA 支持好 | 7B 必须上云 |
| Llama 3.x | 国际主流，英文强 | 中文弱；国内下载麻烦 |
| ChatGLM | 中文好 | 生态与教程相对少 |
| 全参微调 7B | 效果上限高 | 需要 A100 级显存，预算不够 |

### 决策

基座 **Qwen2.5-1.5B-Instruct**（本地 QLoRA）/ **Qwen2.5-7B-Instruct**（云上 QLoRA）。
微调方式 **QLoRA（4bit + LoRA）**。

### 后果

- 正面：能同时讲"小模型本地全流程"和"大模型云上训练"，成本可控（几百元内）
- 负面：QLoRA 的 4bit 量化有精度损失，需在报告中诚实评估
- 重新考虑：若云 GPU 价格异常，只做 1.5B，7B 降级为推理（不训练）

## ADR-007: 仓库骨架最小化起步，不预置空模块

- **日期**: 2025-09-28
- **状态**: 已采纳

### 背景

协作模式为「用户写代码，Agent 做架构设计与评审」。初期若塞入大量空壳模块，
会让人误以为已完成，也违背"每一行代码都自己写过"的学习目标。

### 决策

只提供：目录结构、`.gitignore`、`pyproject.toml`、`environment.yml`、CI 配置、文档。
**不提供任何 `recagent/` 下的实现代码**，模块由用户在每个阶段按需创建。

### 后果

- 正面：学习效果最大化；不会产生"看不懂的既有代码"
- 负面：起步略慢，S0 需要自己动手搭
- 重新考虑：无

## ADR-008: 样板工程由 Agent 代写，算法与评测逻辑必须用户自己写

- **日期**: 2025-09-28
- **状态**: 已采纳（修订 ADR-007）
- **背景事件**: Agent 在自动推进轮中主动实现了完整数据管线
  （`recagent/data/` 7 个模块 + `scripts/` + 4 个测试文件），
  超出 ADR-007 的约定，用户事后确认保留但要求提供导读。

### 背景

ADR-007 的"不预置任何实现代码"过于绝对。实际问题在于：
数据下载校验、日志配置、配置加载这类样板工程**不承载学习目标**，
让用户手写只是消耗时间；而切分、负采样、模型、评测指标承载了
推荐系统的核心正确性认知，代写会直接抹掉学习价值。

### 决策

按「是否承载学习目标」划线，而不是按「是代码还是文档」划线：

| 类别 | 归属 | 例子 |
| --- | --- | --- |
| **样板工程** | Agent 可代写 | 数据下载与 md5 校验、文件解析、日志、配置加载、CI、Dockerfile |
| **算法与正确性逻辑** | 用户必须自己写 | 切分策略、负采样、召回/排序模型、评测指标、Agent 循环 |
| **每次推进前** | Agent 必须先询问 | 任何写实现的动作 |

### 后果

- **正面**：
  - 用户把时间花在真正有学习价值的部分（模型、Transformer、微调、Agent）
  - 样板工程有测试保障，不会成为后续返工的隐患
- **负面**：
  - 边界判断有主观性。本次 `splits.py` / `negative.py` 就落在了
    "算法与正确性逻辑"一侧，本应由用户写，属于越界
  - **补救措施**：产出 `docs/DATA-PIPELINE.md` 导读，
    要求用户读完能复述 6 个自测问题的答案；否则该段经历在面试中是负资产
- **重新考虑**：若用户反馈导读不足以弥补理解缺口，
  应把 `splits.py` / `negative.py` 删除并由用户重写一遍

## ADR-009: 日志统一使用 %-风格占位符

- **日期**: 2025-09-28
- **状态**: 已采纳
- **背景事件**: `download_data.py` 运行到最后一行的
  `logger.info("完成 | {}", report.summary())` 时抛
  `TypeError: not all arguments converted during string formatting`。

### 背景

Python 标准库 `logging` 使用 `%`-风格惰性格式化（`msg % args`），
不支持 `{}`。而项目代码大量使用 f-string 思维写成 `logger.info("{}", x)`，
这类代码**只有在真正输出日志时才崩**，静默期很长，容易漏过。

### 候选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 改用 `loguru` | 支持 `{}`，还有更友好的默认输出 | 多一个依赖；与标准 logging 生态（如库内部日志）整合需额外配置 |
| **统一改 `%`-风格 + AST 守卫测试** | 零依赖；与标准库一致；机器可强制 | 需要一次全量替换；`%` 风格可读性略差 |
| 自定义 `Formatter` 兼容 `{}` | 改动小 | 属于"用魔法绕过约定"，后来者会困惑 |

### 决策

统一使用 `%`-风格，并新增 `tests/test_code_conventions.py`：
用 AST 解析所有源文件，强制
（1）不得出现 `{}` 占位符、
（2）占位符数量必须与参数数量一致、
（3）禁止裸 `except:`。

### 后果

- **正面**：这类错误从"运行时偶发"变成"CI 必然拦截"；不引入额外依赖
- **负面**：`%.1f` 等格式串不如 f-string 直观
- **重新考虑**：若项目后期大量引入结构化日志（JSON logs），
  可重新评估 loguru
