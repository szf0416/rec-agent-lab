# 排查手册：loss 不降 / 训练异常

> 对应 S1 验收标准第 4 条：**能诊断 loss 不降的 5 种原因，以及各自的排查手段**。
>
> 本文所有案例都来自本项目真实踩过的坑，数字可复跑验证。

---

## 零、先看三步（覆盖 80% 的情况）

**不要一上来就调参。** 按这个顺序看，能在 3 分钟内缩小范围：

### 第一步：看 `train_loss` 的趋势

| 观察 | 结论 | 下一步 |
| --- | --- | --- |
| **持续下降** | 模型在学 | → 第二步 |
| **恒定不变** | 梯度为 0，或输出是常数 | → 查原因 2 / 3 |
| **震荡或上升** | 训练不稳定 | → 查原因 1 |
| **一开始就 `nan`/`inf`** | 数值爆炸 | → 查原因 1 / 2 |

### 第二步：看 `valid` 指标与 `train_loss` 的**相对关系**

| train_loss | valid 指标 | 诊断 |
| --- | --- | --- |
| ↓ | **先升后降** | ✅ 正常过拟合 → 加正则（不是 loss 不降） |
| ↓ | **同步下降** | ⚠️ **训练目标与评测目标错配** → 查原因 4 |
| ↓ | 一直不升 | ⚠️ 评测有问题，或任务太难 |
| 高且降不下去 | 差 | ⚠️ **欠拟合** → 查原因 5 |

### 第三步：算 `gap = valid_loss − train_loss`

| gap | train_loss | 诊断 |
| --- | --- | --- |
| 大且扩大 | 低 | 过拟合 |
| 大但稳定 | **高** | **欠拟合**（最容易误判成过拟合）|
| 小 | 低 | 健康 |

### 关键判据：`train_loss` 的值本身

| 看到的数 | 含义 |
| --- | --- |
| **0.6931** | **`ln(2)`** → 二分类输出恒为 0（概率 0.5） |
| `1.0000` / `0.0000` | 完全饱和（可能标签写错）|
| `nan` / `inf` | 梯度爆炸或除零 |

> **异常整齐的数字先怀疑。** `0.6931` 看着像"收敛得漂亮"，
> 实际是模型什么都没学到（见原因 3）。

## 一、原因 1：学习率不当

### 现象

- lr **太大**：loss 震荡、尖峰、甚至 `nan`
- lr **太小**：loss 下降极慢，看起来"卡住了"
- lr **为 0**：loss 完全不变（和原因 2 现象相同，要区分）

### 排查手段

```python
# 1. 直接打印实际使用的 lr（不要看配置，看运行时值）
print(optimizer.param_groups[0]["lr"])

# 2. lr range test：lr 从 1e-6 指数增长到 1e-1，观察 loss
python scripts/exp_optimizer.py --mode lr_range
```

**怎么读 lr range 曲线**：

```
loss
 │＼
 │  ＼___          ← 下降最快的区域 = 可用 lr
 │      ＼___
 │          ＼___  ← 开始上升/震荡 = lr 过大
 └──────────────────▶ lr（对数轴）
 1e-6        1e-1
```

### 本项目案例

```
lr range test 结果：
  下降最快处 lr : 7.75e-04
  建议上界      : 1.29e-02

实验实际选用 lr = 1e-3   ← 同量级，选得合理
```

**踩过的实现坑**：`LambdaLR` 的因子是**乘法**的，实际 `lr = base_lr × factor`。
我第一次把 `base_lr` 设成 `1.0`，结果实际 lr 跑到 `3e5`，
range test 输出 `下降最快处 lr = 4.16e+01`（**超过扫描上界 0.03 一百倍**）。

> **教训**：**结果出现越界值（超出设定范围）时，一定是实现有问题**，
> 不要当成"模型行为异常"。

## 二、原因 2：梯度问题

### 现象

- 梯度**没有回传**：loss 完全不变
- 梯度**爆炸**：loss 变 `nan`
- 梯度被**过度裁剪**：学习停滞

### 排查手段

```python
# 1. 梯度是否为 None（忘了 backward？）
for name, p in model.named_parameters():
    print(name, p.grad is None)

# 2. 梯度范数（是否爆炸 / 是否接近 0）
total = sum(p.grad.norm() ** 2 for p in model.parameters() if p.grad is not None) ** 0.5
print("grad norm:", total)

# 3. 参数是否真的在变
before = {k: v.clone() for k, v in model.state_dict().items()}
optimizer.step()
for k, v in model.state_dict().items():
    if torch.equal(before[k], v):
        print(f"{k} 没有变化！")
```

### 常见根因

| 根因 | 表现 |
| --- | --- |
| 忘了 `loss.backward()` | 所有 `.grad` 为 `None` |
| `zero_grad()` 放错位置 | 梯度累加导致等效 lr 放大 |
| `torch.no_grad()` 包住了训练循环 | 计算图没构建，梯度为 `None` |
| 梯度裁剪阈值过小 | grad_norm 恒等于阈值，学习停滞 |
| 损失函数用了 `detach()` | 梯度链断裂 |

### 本项目相关经验

训练循环里记录了 `grad_norm_history`，**用它可以一眼看出问题**：

```python
history.grad_norm_history   # 若为空 → 说明 grad_clip=None 或没进入 step
```

> 这也是"记录粒度"的价值 —— 不记录就查不了。

## 三、原因 3：优化器与正则组合不当（本项最隐蔽）

### 现象

**`train_loss` 卡在 `0.6931 = ln(2)`，一动不动。**

`ln(2)` 是二分类交叉熵在"输出概率恒为 0.5（logits 恒为 0）"时的值 ——
**说明模型输出完全退化，什么都没学到**。

### 根因

`Adam(weight_decay=w)` 走 **L2 路径**：把 `w·θ` 加进**梯度**。

```python
# Adam 内部（简化）
g = grad + weight_decay * param     # ← 衰减项进了梯度
m = beta1 * m + (1 - beta1) * g
v = beta2 * v + (1 - beta2) * g ** 2
param -= lr * m / (sqrt(v) + eps)   # ← 自适应归一化把衰减放大
```

**问题出在稀疏参数（embedding）上**：

```
embedding 表大小         : 396,800 行
每 batch 激活的行        : ~1.3 万（约 3%）
weight_decay 作用范围    : 100% 的行

→ 97% 的参数被衰减，却得不到梯度抵抗
→ 且衰减经 m/√v 归一化后被放大成一次完整更新
→ 整体被单向拉向 0
```

**实质是"惩罚冷门物品"** —— 越冷门的物品越少被激活，
越少得到梯度抵抗衰减，越快趋近 0。这与推荐系统的长尾目标直接冲突。

### 排查手段

```python
# 1. calc: train_loss 是否恰好等于 ln(2)？
import math
if abs(train_loss - math.log(2)) < 1e-3:
    print("⚠️ loss = ln(2)，模型输出恒为 0，先查优化器与 weight_decay")

# 2. 检查模型输出的标准差
print("prediction std:", predictions.std())   # 若 ≈ 0 → 输出是常数

# 3. 检查参数的范数是否在持续缩小
print("param norm:", sum(p.norm() for p in model.parameters()))
```

### 本项目实测数据（S1-W4）

同样的 `weight_decay=0.01`，只换优化器：

| 配置 | train_loss | ndcg最优 | 相对无 wd |
| --- | --- | --- | --- |
| `adam`（无 wd） | 0.0452 | 0.1706 | — |
| **`adam + wd 0.01`** | **0.0591** | **0.0468** | **−73%** |
| `adamw`（无 wd） | 0.0452 | 0.1706 | — |
| **`adamw + wd 0.01`** | 0.0459 | **0.1705** | **−0.06%** |

**差 3.6 倍。** `adam + wd` 的 `0.0468` 已接近随机水平（100 候选随机 ≈ 0.014）。

### 修法

**用 `AdamW`**（权重衰减解耦出梯度）：

```python
# AdamW
param -= lr * (m / (sqrt(v) + eps) + weight_decay * param)
#                 ↑ 数据驱动              ↑ 衰减，不被自适应缩放
```

衰减恒为 `lr × w × θ`，不会被放大。

> **面试可讲**：这是「推荐系统必须用 AdamW」最硬的证据。
> 不是理论推演，是同 wd 下 `0.0468 vs 0.1705` 的实测对比。

## 四、原因 4：数据问题

### 现象

- **loss 异常低**（比预期好太多）→ 通常是**数据泄漏**
- loss 异常高 → 标签或对齐有问题
- 训练正常但评测指标不涨 → **评测协议错配**

### 四类必须检查的数据问题

| 类型 | 检查方法 |
| --- | --- |
| **标签泄漏** | 输入里是否包含了要预测的标签？（本项目：`sequences_train.npz` 的序列末项就是下一个物品，直接当输入等于让模型抄答案）|
| **未来信息泄漏** | 时间切分是否正确？（本项目：切点必须落在严格时间边界上）|
| **负样本污染** | 负样本是否与正样本重叠？（本项目：候选集长度从 101 变 100 导致 collate 报错）|
| **评测协议错配** | 训练与评测的候选集协议是否一致？ |

### 本项目案例：评测协议错配

**现象**：

```
epoch 0:  train_loss=0.6221   valid_ndcg=0.1445
epoch 9:  train_loss=0.4952   valid_ndcg=0.1312   ← 两者同步下降
```

**误判**：以为是过拟合。
**真因**：训练负样本**每轮动态重采样**，评测负样本**固定**。
模型不断适应新的随机负样本分布，而评测用的是固定那 100 个候选
→ **训练目标 ≠ 评测目标**，loss 下降不代表评测变好，**评测信号失效**。

**修法**：训练负样本也一次性固定。

**意外收益**：训练提速 **12 倍**（32 秒/轮 → 2.6 秒/轮），因为负样本预计算后可复用。

> **判据**：`train_loss ↓` 且 `valid 指标 ↓`（**同步下降**）→ 先怀疑协议错配，
> 而不是过拟合。过拟合的曲线是 `valid` **先升后降**。

### 本项目案例：标签泄漏

`sequences_train.npz` 里的序列是「该用户训练期最近 50 条交互」，
**末项就是下一个物品本身**。若直接用整段序列当输入、末项当标签：

```python
input = seq            # [i1, ..., i49, i50]
label = seq[-1]        #                  ↑ 就是 i50
# → 模型只要输出 input 的最后一项就能完美预测
```

**修法**：`输入 = seq[:-1]`，`标签 = seq[-1]`。

> 这类泄漏让指标**变好**，比指标变差更难发现。

## 五、原因 5：模型容量与结构问题

### 现象

`train_loss` **本身就高**，怎么训都降不下去（欠拟合）。

### 排查手段

```python
# 1. 参数量够不够？
print(sum(p.numel() for p in model.parameters()))

# 2. train_loss 是否本身就高？（这是欠拟合的直接判据）
#    不要只看 gap，要看 train_loss 的绝对值

# 3. 激活是否饱和？（sigmoid/tanh 在极端输入处导数→0）
print(activations.abs().max())   # 若很大 → 饱和
```

### 本项目案例

去掉 MLP 打分头、只留内积（`capacity_nomlp`）：

| 配置 | 参数量 | train_loss | gap | ndcg最优 |
| --- | --- | --- | --- | --- |
| baseline（含 MLP） | 572K | **0.0439** | 0.0117 | **0.1706** |
| `capacity_nomlp` | 506K | **0.4905** | 0.0773 | **0.1465** |

**注意 `train_loss = 0.4905`** —— 比 baseline 高 **11 倍**。

这是**欠拟合**：模型表达能力不足，连训练集都拟合不好。

**关键区分**：

| | train_loss | gap | 对策 |
| --- | --- | --- | --- |
| 过拟合 | 低 | 大 | 加正则 / 降容量 |
| **欠拟合** | **高** | 大 | **加容量 / 减正则** |

**对策方向相反。** 如果 `capacity_nomlp` 被误判成过拟合而去加 dropout，
只会更糟（本来就学不动，再丢信息）。

## 六、快速检查清单

遇到训练异常时，按顺序过一遍：

```
□ 1. 打印 train_loss 趋势 —— 下降/恒定/震荡/nan？
□ 2. train_loss 是否恰好是 0.6931（ln(2)）？→ 原因 3
□ 3. 打印实际 lr（运行时值，不是配置）→ 原因 1
□ 4. 有梯度吗？.grad 是 None 吗？范数多大？→ 原因 2
□ 5. valid 指标与 train_loss 是同步降还是先升后降？→ 原因 4
□ 6. train_loss 绝对值本身高不高？→ 原因 5
□ 7. 数据检查：标签在输入里吗？切分有泄漏吗？负样本撞正样本吗？
□ 8. 优化器与 weight_decay 的组合是什么？→ 原因 3
```

---

## 七、三条元规则

1. **异常整齐的数字先怀疑**
   `0.6931 = ln(2)`、`1.0000`、`0.0000` —— 这些"漂亮"的值通常意味着退化。

2. **「结果很好」比「结果很差」更危险**
   结果差你会查；结果好你会直接采信。
   本项目踩过两次：`ndcg=1.0`（指标平局 bug）和 `ln(2)`（embedding 被压死）。

3. **修完一个问题，扫一遍同类**
   `.gitignore` 的 `data/` 修完没检查 `models/`，同一个坑犯了两次。
