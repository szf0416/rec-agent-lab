## 三、必答问题 1：为什么 Adam 收敛快，但有时泛化差？

### 收敛快的原因

Adam 同时做了两件事：

```
m = β₁m + (1-β₁)g          ← 一阶矩：动量，抑制震荡
v = β₂v + (1-β₂)g²         ← 二阶矩：记录梯度的历史尺度
θ ← θ − lr · m / (√v + ε)  ← 自适应步长：每个参数独立缩放
```

最后那个 `m/√v` 是关键：**每个参数的有效步长与该参数历史梯度尺度无关**。
梯度小的参数会被放大，梯度大的参数会被压缩 —— 相当于给每个参数配了独立学习率。

对推荐系统尤其重要：embedding 表里热门物品和冷门物品的激活频率差几个数量级，
Adam 的自适应性天然缓解了这个不平衡。

**本项目实测**（S1-W4）：

| 优化器 | ndcg最优 |
| --- | --- |
| Adam | **0.1706** |
| SGD + Momentum | 0.0600 |
| SGD | 0.0493 |

**差 3.5 倍。** 而且 SGD 的 `train_loss` 只到 0.0560（Adam 是 0.0452），
说明连收敛都没充分。

### 泛化可能差的原因（三层）

**第一层：自适应步长在训练后期放大噪声。**

`m/√v` 的归一化意味着：即使梯度已经很小，步长仍接近 `lr`。
模型在极小值附近**持续跳动**，倾向于收敛到**尖锐极小值（sharp minima）**。
而尖锐极小值对参数扰动敏感 → 泛化差。

SGD 的梯度噪声反而有**正则效果**，倾向于收敛到平坦极小值。

> 这也是为什么有 SWA、Lookahead 这类"后期转 SGD"的方法。

**第二层：权重衰减与自适应耦合（本项目有硬证据）。**

`Adam(weight_decay=w)` 把 `w·θ` 加进梯度。对**稀疏参数**（embedding）后果严重：

```
embedding 表                : 396,800 行
每 batch 激活的行            : ~3%
weight_decay 作用范围        : 100% 的行

→ 97% 的参数被衰减却得不到梯度抵抗
→ 衰减经 m/√v 归一化被放大成一次完整更新
→ 整体被单向拉向 0
```

**实测**（同样 `wd=0.01`，只换优化器）：

| 配置 | train_loss | ndcg最优 |
| --- | --- | --- |
| `adam` 无 wd | 0.0452 | 0.1706 |
| **`adam` + wd 0.01** | 0.0591 | **0.0468**（−73%）|
| `adamw` 无 wd | 0.0452 | 0.1706 |
| **`adamw` + wd 0.01** | 0.0459 | **0.1705**（−0.06%）|

**差 3.6 倍。** 修法是 `AdamW`（衰减解耦出梯度，恒为 `lr×w×θ`）。

**第三层：batch size 与学习率的耦合。**

Adam 的自适应尺度依赖 batch 内的梯度统计。
batch 太小时，`v` 的估计噪声大，步长不稳定 —— 这也是大 batch 训练
常配合 lr 调整的原因（但**线性缩放不是普适的**，我们实测 batch×4 时
放大 lr 反而更差：0.1701 → 0.1663）。

### 一句话回答（面试用）

> "Adam 收敛快是因为**每个参数有自适应步长**，对稀疏的 embedding 尤其友好
> （我们实测比 SGD 高 3.5 倍）。泛化差主要有两个原因：
> 一是 `m/√v` 归一化让后期步长不衰减，容易停在尖锐极小值；
> 二是 `weight_decay` 与自适应耦合，在稀疏参数上会**压死 embedding** ——
> 我实测过同样 `wd=0.01`，Adam 的指标从 0.1706 崩到 0.0468，而 AdamW 几乎无损。
> 所以我用 AdamW。"

## 四、必答问题 2：BatchNorm 训练/推理为什么不同？

### 机制（第一层）

```
训练:  y = γ · (x − μ_batch) / √(σ²_batch + ε) + β
推理:  y = γ · (x − μ_running) / √(σ²_running + ε) + β
```

训练用**当前 batch** 的统计量，推理用**训练期累积的滑动平均**。

### 为什么必须分开（第二层，这是重点）

**理由 1：推理时可能只有 1 个样本。**

```
单样本的 batch 方差恒为 0
→ √(0 + ε) ≈ 0.003
→ 输出全变成 0，信息完全丢失
```

**实测**：

```
输入          : [5, 3, -1, 2]
batch 方差    : [0, 0, 0, 0]        ← 全 0
强行归一化结果: [0, 0, 0, 0]        ← 信息丢失
用滑动平均    : [3.52, 1.93, -1.15, 1.05]   ← 有意义
```

**理由 2：线上请求是逐条来的，行为必须确定。**

如果推理也用 batch 统计，同一个用户在不同并发批次里会得到**不同推荐**。
实测训练模式下同一个样本放入不同 batch，输出差异达 **6.3753**。

**理由 3：训练/推理要用同一套"规则"才能保证效果。**

训练时参数是基于 batch 统计学的，推理时用全局统计才是一致的近似。

### 实现细节（第三层，容易写错）

**滑动平均里存的是「无偏」方差（除以 N−1），而归一化用的是「有偏」（除以 N）。**

```python
var_biased   = x.var(axis=0)                        # 归一化用
var_unbiased = var_biased * N / (N - 1)             # 更新 running_var 用
```

两者相对差距正好是 `1/N`（N=16 时 6.25%）。
本项目手写实现与 PyTorch 的 `running_var` 对齐到 **2.220e-16** ——
说明这个细节处理正确。

### 一句话回答（面试用）

> "训练用**当前 batch** 的均值方差归一化，推理用**训练期累积的滑动平均**。
> 为什么必须分开：推理时可能只有 1 个样本，batch 方差恒为 0，
> 强行归一化会把输出全压成 0、信息丢失；而且线上请求逐条来，
> 用 batch 统计会让同一用户在不同批次得到不同结果。
> 实现上还有个细节：滑动平均存的是**无偏**方差，归一化用**有偏** ——
> 我的实现和 PyTorch 对齐到了 1e-16 量级。"

## 六、踩过的坑（S1 全阶段汇总）

### 我写代码时犯的（值得记的）

| 坑 | 教训 |
| --- | --- |
| `.gitignore` 的 `data/` 忽略掉代码包 | 修完没扫同类，`models/` 又犯一次 |
| `logger.info("{}")` 用错占位符 | 标准 logging 只支持 `%s`，边界行为要实测 |
| `torch.sqrt(0.0)` 抛异常 | 库的类型接受度不能凭记忆 |
| 测试断言里 `accumulator := 3` | 写完没跑就交付 |
| 排序指标平局 bug | **"结果很好"比"结果很差"更危险** |
| `OptConfig.momentum` 默认值 0.9 | 两个配置结果完全相同时，先怀疑配置重复 |
| `LambdaLR` 的 `base_lr` 用错 | **结果越界时一定是实现有问题** |
| BN 的 dtype 不匹配 | float64 输入要记得 `.double()` 模型 |
| 有偏/无偏方差差距算成 1/(N−1) | 实际是 1/N。精确的断言连作者的错误也能抓 |

### 设计上犯的

| 坑 | 教训 |
| --- | --- |
| 训练负样本动态 + 评测固定 → 评测信号失效 | **采样协议可以不同，但"候选集是否固定"必须一致** |
| 模型容量不足 → 过拟合观察不到 | **做正则化实验前先确认能造出可观察的过拟合** |
| 验证集用户与训练集不匹配 | 评测集必须与训练同分布，否则测的不是泛化 |
| 候选集长度不齐 → collate 崩溃 | 涉及 `torch.stack` 的数据要显式断言长度 |
